# Notification Platform

**Status:** Phase 1 (foundation) and the Submissions integration are built and verified end-to-end. This is a separate capability from the RBAC/permission system described in `01`–`07` — read together with `05-enforcement-strategy.md`'s "ownership vs. module visibility" framing, not as a replacement for it.

## Why this exists — three distinct concepts

GovernanceOS has three different things that all look superficially similar ("something shows up telling a user about something") but have different purposes, different audiences, and different security models. Conflating them was the risk this document exists to prevent.

| | Global Search | Governance Alerts | Personal Notifications |
|---|---|---|---|
| **Audience** | Whoever is searching | The organization | One specific user |
| **Purpose** | Aggregate results across modules | Org-wide governance events (compliance deadlines, license expiry, capital breaches) | Notify a user about work that belongs to them |
| **Security model** | Filtered by the caller's existing `*.view` permissions per result category | Module RBAC (`alert.view`/`alert.update`/`alert.generate`) | **Ownership**, not RBAC — see below |
| **Where it lives** | `app/api/search/route.ts` | `Alert` model, `lib/alertEngine.ts`, `/alerts` | `Notification` model, `lib/notifications/`, `/api/me/notifications` |
| **This document covers** | No (see `07-implementation-log.md`) | No — explicitly not redesigned | Yes |

## The architectural rule

> **Ownership supersedes module visibility for personal work queues.**

A user must always be able to see work that belongs to them, even if their role no longer grants visibility into the parent module. Concrete example: a user is assigned a Compliance obligation; later their role loses `compliance.view`; they should still see that it's theirs, because that relationship was never a module-browsing permission in the first place. Personal notification endpoints therefore:

- Require an authenticated session.
- Filter by the authenticated user's own id (`recipientId`).
- **Never** call `authorizeRequest()`, never check any `*.view` permission.

Authentication + ownership is the complete authorization model for everything under `/api/me/notifications`.

## Existing legacy feed — investigated, not migrated

`GET /api/notifications/tasks` already follows this rule *in design* — session-required, filtered by `owner: session.user.name` — but its ownership match is fragile: `ComplianceObligation.owner` is a free-text `String`, and `User.name` isn't even unique (`schema.prisma` — only `email` is `@unique`). This is documented technical debt, deliberately **not fixed**. It continues to power the bell exactly as it did before. The target state is Compliance eventually migrating onto the model below, where ownership is a real `User.id` foreign key from the start — not something to retrofit onto the legacy feed piecemeal.

## Data model

```prisma
enum NotificationType {
  SUBMISSION_STATUS_CHANGED
  APPROVAL_REQUESTED   // defined, not yet triggered by any module
  TASK_ASSIGNED        // defined, not yet triggered by any module
  DOCUMENT_SHARED      // defined, not yet triggered by any module
  MEETING_ASSIGNED     // defined, not yet triggered by any module
}

enum NotificationEntityType {
  SUBMISSION
  DOCUMENT
  BOARD_MEETING
  COMPLIANCE_OBLIGATION
}

model Notification {
  id          String   @id @default(cuid())

  recipientId String
  recipient   User     @relation("NotificationRecipient", fields: [recipientId], references: [id], onDelete: Cascade)

  actorId     String?
  actor       User?    @relation("NotificationActor", fields: [actorId], references: [id], onDelete: SetNull)

  type        NotificationType
  entityType  NotificationEntityType
  entityId    String

  title       String   // generated by the service at creation time — never caller-supplied
  message     String   // same
  url         String   // same, derived from entityType/entityId

  metadata    Json?
  readAt      DateTime?
  createdAt   DateTime @default(now())

  @@index([recipientId, readAt])
  @@index([recipientId, createdAt])
}
```

Two deliberate design choices worth calling out:

- **`recipientId` cascades on delete; `actorId` sets null on delete.** If the recipient is deleted, their notification history goes with them. If the actor is deleted, the notification is still meaningful to the recipient and survives, just with the actor reference cleared — getting this backwards would silently wipe a recipient's history whenever an unrelated actor's account was removed.
- **`title`/`message` are computed once, at creation time, and stored** — not derived live on every read. This mirrors `AuditLog.oldValues`/`newValues`: a notification is a historical record, so a later change to the actor's display name should never retroactively reword past notifications.

Migration: `prisma/migrations/20260730120647_add_notifications/`.

## Service layer — `lib/notifications/`

```
lib/notifications/
  service.ts      createNotification(), markRead(), markAllRead(), listForUser()
  templates.ts    private per-type title/message templates + entityType → URL map
```

**No `types.ts`** — `NotificationType`/`NotificationEntityType` are Prisma enums; importing them directly from `@prisma/client` keeps a single source of truth instead of a duplicate re-export.

**`createNotification()` is the only place allowed to write to the `notifications` table.** No module should ever call `prisma.notification.create(...)` directly — every integration goes through the service, exactly the discipline the existing `Alert` model *doesn't* have today (each module effectively invents its own alert logic; this is deliberately not repeated here).

```ts
createNotification({
  type: NotificationType;
  recipientId: string;
  actorId?: string | null;
  entityType: NotificationEntityType;
  entityId: string;
  metadata?: Record<string, unknown>;
})
```

The caller never supplies `title`/`message`/`url`. Business intent goes in; the service is responsible for generating presentation. This prevents every module from inventing its own wording and navigation logic:

```text
Module's mutation handler (already permission-checked)
        │  business logic succeeds
        ▼
createNotification({ type, recipientId, actorId, entityType, entityId, metadata })
        │
        ▼
templates.ts: renderNotification(type, { actorName, metadata }) → { title, message }
templates.ts: buildNotificationUrl(entityType, entityId) → url
        │
        ▼
notifications table (one row, fully formed)
```

`markRead(notificationId, recipientId)` and `markAllRead(recipientId)` both take `recipientId` as a required parameter — ownership is enforced at the data layer (a `WHERE recipientId = ...` on every mutating query), not left for each API route to remember to check separately.

## API

```text
GET   /api/me/notifications             — list, optional ?unreadOnly=true
PATCH /api/me/notifications/:id/read    — mark one read
PATCH /api/me/notifications/read-all    — mark all read
```

All three: `getAuthSession()` → `401` if none → delegate to the service using `session.user.id`. No `authorizeRequest()`, no permission constant, anywhere in this path.

## Bell integration (temporary MVP state)

The bell (`components/layout/Header.tsx`) currently renders **two sources merged only for display**, not normalized into a shared data model:

```text
GET /api/notifications/tasks   ─┐
                                 ├─▶ merge, sort by date ─▶ render in one dropdown
GET /api/me/notifications      ─┘
```

- Legacy items: click → navigate only (unchanged from before this work).
- Platform items: click → `PATCH /api/me/notifications/:id/read` → navigate.
- Badge count = legacy task count (no read state exists for them) + unread platform count.

This is intentionally not the end state. The two sources will run in parallel until Compliance migrates onto the new platform, at which point the bell does **one atomic cutover** to the unified source and `/api/notifications/tasks` is retired — avoiding an extended period of two live sources being reconciled piecemeal.

## Submissions integration (the one live producer)

```text
PATCH /api/submissions/:id
        │
        ▼
findUnique()  ── capture existing.status
        ▼
authorizeRequest(SUBMISSION_APPROVE | REJECT | STATUS_UPDATE)   ← unchanged RBAC check
        ▼
update()      ── produces the new, persisted sub.status
        ▼
sub.status !== existing.status ?  ──no──▶ done, no notification
        │yes
        ▼
resolveSubmitterId(existing.submittedBy)   ── email lookup, then name fallback
        │
   found? ──no──▶ log + skip (no notification; see limitation below)
        │yes
        ▼
createNotification({ type: SUBMISSION_STATUS_CHANGED, recipientId, actorId: session.user.id, entityType: SUBMISSION, entityId: sub.id, metadata: { submissionTitle, oldStatus, newStatus } })
```

The comparison is on the two **persisted** rows (`existing` vs. the just-`update()`d row), not the incoming request body — an `approved → approved` no-op payload correctly produces nothing.

**Deliberately not implemented:** a notification on *creation*. The only person involved when a submission is created is the submitter — there's no "notify reviewers a new submission needs attention" concept yet, which would need a role/group recipient, not an individual owner, and is out of scope for this phase.

### Known dependency for future extension

`Submission.submittedBy` is a free-text `String`, not a `User.id` foreign key. `resolveSubmitterId()` works reliably for every submission created after the RBAC fix that made `submittedBy` always session-derived (never client-trusted) — but any legacy row predating that fix (old hardcoded values, team-name strings) may not resolve to any user, in which case no notification is created rather than guessing. A future phase should either add a real `submitterId` FK via migration, or formalize the lookup-with-documented-fallback approach used today.

## Verified end-to-end

- Created a submission, changed its status through the admin console → confirmed a `Notification` row was created with the correct `recipientId` (resolved from `submittedBy`), correct `title`/`message`/`url`, and `readAt: null`.
- Confirmed the bell surfaces it and the badge count reflects it.
- Confirmed clicking it in the bell calls the mark-read endpoint and `readAt` gets set.
- Confirmed a status no-op (`approved → approved`) produces no new row.
- One real bug found and explained during verification, not a code defect: a running `next dev` process caches its `PrismaClient` instance across hot-reloads (`lib/prisma.ts`'s `globalForPrisma` pattern) — after adding the `Notification` model, the already-running server had a stale client in memory until restarted. Calling the service directly in a fresh process succeeded immediately, confirming the model/service/templates were correct all along; only the long-running dev server needed a restart to pick up the regenerated Prisma Client.
